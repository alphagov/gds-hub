## What was built

- A Drizzle ORM schema for 16 tables and 5 Postgres enums, in `src/db/schema/`, following Section 6.
- `drizzle.config.ts` and the `db:generate`, `db:migrate`, `db:seed` and `db:reset` scripts.
- A hand-written migration, `drizzle/0001_search.sql`, that adds generated, weighted `tsvector` columns, GIN indexes and the `search_index` view.
- A hand-written migration, `drizzle/0002_audit_log_append_only.sql`, that makes `audit_log` append-only.
- A synthetic seed covering every table and page type, with an `audit_log` entry for every row.
- A Vitest integration test that creates a throwaway database, migrates and seeds it, and checks:
  - the tables, enums and search columns
  - that foreign keys are enforced, including RESTRICT and CASCADE
  - the check constraints, including link and GitHub name formats
  - that `audit_log` entries can be added but not changed, deleted or truncated
  - that no column could hold credentials
  - that the search index includes the right records and ranks results
- Guards that stop `db:reset` and `db:seed` changing anything but a local development database, with unit and integration tests.
- A CI step that fails if `src/db/schema` changes without a matching migration.

## Data model

Every table has a `bigint` identity `id`. Every table except `audit_log` has `created_at` and `updated_at` (`timestamptz`, default `now()`). `audit_log` has only `created_at`. Keys and slugs must be kebab-case (a CHECK constraint).

There are two kinds of date. `updated_at` changes on every write. `last_reviewed_at` (on instances, product team services and pages) is set by a person and means the content was checked as accurate.

| Table                                 | Purpose                                                    | Foreign keys (on delete)                                                                                          |
| ------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `vendors`                             | Company that makes a tool (has a `slug`)                   | none                                                                                                              |
| `suppliers`                           | Company GDS buys through (may be a reseller)               | none                                                                                                              |
| `tools`                               | A software product                                         | `vendor_id` → vendors (restrict, **nullable**)                                                                    |
| `supplier_tools`                      | Which suppliers supply which tools                         | supplier, tool (cascade)                                                                                          |
| `contracts`                           | A licence agreement for a tool with a supplier             | `tool_id`, `supplier_id` (restrict)                                                                               |
| `ownership_levels`                    | EE ownership maturity levels                               | none                                                                                                              |
| `instances`                           | A deployment, account or tenant of a tool                  | `tool_id` (restrict), `contract_id` + `tool_id` → contracts (restrict, **nullable**), ownership levels (restrict) |
| `capabilities`                        | Functional capability, grouped by `group_name`             | none                                                                                                              |
| `capability_tools`                    | Which tools provide which capabilities                     | capability, tool (cascade)                                                                                        |
| `product_team_services`               | Product, team, service or community (has a `slug`)         | none                                                                                                              |
| `product_team_service_instances`      | Which instances a team uses                                | team, instance (cascade)                                                                                          |
| `instance_capabilities`               | Which capability an instance provides to which team        | instance, capability, team (cascade)                                                                              |
| `business_units`                      | Directorate or other business unit, can nest               | `parent_id` → business_units (restrict)                                                                           |
| `business_unit_product_team_services` | Which teams each business unit operates                    | business unit, team (cascade)                                                                                     |
| `pages`                               | Long-form markdown content, globally unique `slug`         | `product_team_service_id` → product_team_services (restrict, nullable)                                            |
| `audit_log`                           | One row per change, with the full row `before` and `after` | none (`entity_id` deliberately has no FK)                                                                         |

Not created: `admin_users`, `roles`, `active_admin_comments` and `versions` (replaced by `audit_log`). There are no credential columns, and a test checks `information_schema` for any.

### Enums

| Enum                           | Values                                                        | Used by                              |
| ------------------------------ | ------------------------------------------------------------- | ------------------------------------ |
| `migration_status`             | `not_started`, `in_progress`, `complete`                      | `instances.migration_status`         |
| `engineering_or_business_tool` | `engineering`, `business`                                     | `tools.engineering_or_business_tool` |
| `page_type`                    | `policy`, `service_guide`, `guidance`, `general`, `whats_new` | `pages.page_type`                    |
| `content_status`               | `draft`, `published`                                          | `pages.status` (default `published`) |
| `audit_action`                 | `create`, `update`, `delete`, `publish`, `unpublish`          | `audit_log.action`                   |

Adding an enum value is backward compatible. Removing or renaming one isn't, so treat these lists as append-only. `hub_role` from Section 6 is Phase 7 only and isn't created.

### `audit_log` columns

`entity_type` (`varchar(64)`, the singular record type such as `instance` or `page`, from `src/db/entity-types.ts`), `entity_id`, `action`, `before` and `after` (the full row as `jsonb`), `changed_fields` (`jsonb` list, default `[]`), `actor_name` and `actor_subject` (both the editor's email in the MVP, `system:...` for the seed and imports), `source_ip`, `request_id`, `change_summary` and `created_at`. Index `audit_entity_idx` on `(entity_type, entity_id, created_at)`.

**`audit_log` is append-only.** Triggers in `drizzle/0002_audit_log_append_only.sql` reject `UPDATE`, `DELETE` and `TRUNCATE` on it, whichever code path tries. Dropping the table or database (`db:reset`, test clean-up) still works. A future retention policy needs a deliberate step by the table owner that disables the triggers.

### `pages` columns

`slug` (`varchar(160)`, unique), `title` (`varchar(255)`), `page_type`, `summary`, `body_markdown`, `owner_name`, `owner_contact`, `product_team_service_id`, `status` (default `published`), `last_reviewed_at`, `published_at`, `created_at` and `updated_at`.

### Check constraints

- Kebab-case `key` on tools, instances, ownership levels, capabilities, product team services and business units. Kebab-case `slug` on vendors, tools, instances, product team services and pages.
- A business unit can't be its own parent.
- On contracts, `end_date >= start_date` when both are set.
- `instances.extra_attributes` must be a JSON object whose values are all text.
- Link columns must be absolute `http` or `https` URLs with no spaces: `url` on vendors, suppliers, instances, business units and product team services, and `product_team_services.slack_channel`.
- Each `product_team_services.gh_orgs` entry must be a valid GitHub name: letters and digits, with single hyphens between them. No empty or null entries.
- On `audit_log`:
  - `actor_name` and `actor_subject` can't be blank, and `changed_fields` must be a JSON list.
  - A `create` has only `after`, a `delete` has only `before`, and `update`, `publish` and `unpublish` have both.

### Search

`drizzle/0001_search.sql` adds a `search_vector tsvector GENERATED ALWAYS AS (...) STORED` column (the `english` configuration) and a GIN index to these tables:

| Table                   | A (title) | B (summary) | C (body)                            |
| ----------------------- | --------- | ----------- | ----------------------------------- |
| `vendors`               | name      | description | none                                |
| `tools`                 | name      | description | none                                |
| `instances`             | name      | description | getting_access, management, support |
| `capabilities`          | name      | description | comment                             |
| `product_team_services` | name      | purpose     | none                                |
| `business_units`        | name      | description | none                                |
| `ownership_levels`      | name      | definition  | description, target_state           |
| `pages`                 | title     | summary     | body_markdown                       |

The `search_index` view is a UNION ALL of these tables with the columns `entity_type`, `entity_id`, `slug`, `title`, `summary`, `snippet_source`, `search_vector` and `updated_at`.

- `slug` is the record's URL identifier. Capabilities, business units and ownership levels have no slug column, so they use `key`.
- `snippet_source` is the B and C text, for `ts_headline` snippets in the Section 6.4 query.
- Only published pages are included. Suppliers and contracts are left out because they hold commercial information.

### Differences from Section 6

Chosen by the developer:

- **`whats_new` page type** added alongside Section 6's four, for the current Hub's dated "What's new" posts.
- **`business_units` and `ownership_levels` are searchable** as well as Section 6.4's six tables.

Smaller choices where Section 6 doesn't specify:

- `pages.product_team_service_id` uses RESTRICT on delete, like the other links between entities.
- Columns on the tables that already existed stay `text`. Section 6 only gives `varchar` lengths for `pages` and `audit_log`, so those two use them.
- Contract `cost` and `total_users` stay `text`, because Section 6 says "consider… if existing data allows", and the build summary records `total_users` as "string/number". Check the real values in Phase 5 before converting either.
- Join-table foreign key columns that lead a composite unique index don't have a second index of their own. The unique index already serves lookups on that column.

## Decisions

- **Where the prototype differs from the YAML relationships:**
  - **Tool-level YAML fields live on instances, as in the prototype.** These are url, management, getting access, current and target ownership level, migration status and date, not in use, service desk support and support. Phase 5 creates a placeholder instance (`is_placeholder = true`) for each tool that has no real instances.
  - **Commercial YAML fields live on contracts.** These are the cost model, commercials, licence dates, number of users, operational policy and data protection. A contract needs a supplier, and the YAML has no supplier data. **Open question for Phase 5:** create one placeholder supplier, or make `contracts.supplier_id` nullable.
  - **A team's `uses[]` (team → tool) becomes team → instance** (`product_team_service_instances`), as in the prototype. Phase 5 links each team to the tool's instance, or its placeholder instance.
  - **Business unit → team is many-to-many** (a join table), so a team can sit in more than one unit, as the current data allows. The current Hub's "first business unit wins" rule for URLs and navigation isn't modelled. Phase 4 or 5 decides this, for example by adding a "primary" flag.
  - **Fields the prototype was missing were added** so Phase 5 doesn't lose data:
    - instances: `not_in_use`, `supported_by_gds_software_service_desk`, `support`, `migration_date`
    - product team services: `slack_channel_name`, `team_email_address`, `gh_orgs text[]`
    - contracts: `cost_model`
  - **The capability group stays a plain text label** (`group_name`), as in the current Hub.
- **`tools.vendor_id` and `instances.contract_id` are nullable** (the developer's decision), because the current data has no vendors or contracts.
  - **`instances.tool_id` was added as a consequence.** In the prototype, an instance reached its tool only through its contract. Making `contract_id` optional would have cut that link.
  - **A composite foreign key keeps the two consistent.** `(contract_id, tool_id)` references `contracts(id, tool_id)`, so an instance's contract must be for the same tool. A null `contract_id` skips the check.
- **The two prototype columns with type problems are fixed:** `instances.target_ownership_level_id` and `business_units.parent_id` are `bigint` with real foreign keys.
- **`key` and `name` are NOT NULL everywhere.** The prototype left several of them nullable.
- **What happens on delete:** RESTRICT between entities, so you can't delete a vendor, tool, contract, ownership level, parent unit, or a team with pages, while something still uses it. Postgres reports this as `23001` (`restrict_violation`). CASCADE on join tables.
- **Foreign keys on the join tables have explicit short names.** The generated names would go over Postgres's 63-character limit.
- **Enum values are lower snake case.** Phase 5 maps the YAML strings: for example, `"Not started yet"` becomes `not_started`, `"Migration to DSIT complete"` becomes `complete`, and `"Business Tool"` becomes `business`. Any other migration statuses in the real data need confirming before Phase 5.
- **The search columns and view live in a hand-written migration, not the Drizzle schema.** drizzle-kit only diffs its own snapshots, so it leaves them alone, and the view is declared `.existing()` for typed reads in Phase 10. **A future migration that changes a column used by search must drop and recreate the view and the affected `search_vector` column.**
- **`audit_log` has no foreign key on `entity_id`,** so the history survives deletes. The seed stores `before`, `after` and `changed_fields` using Drizzle's property names (camelCase). Phase 3 should confirm this convention.
- **`updated_at` isn't updated by a trigger.** Repositories set it (Phase 3).
- **The seed:**
  - Only synthetic data: invented organisations, tools and teams, `example.com` addresses and `example.slack.com` links.
  - Runs in one transaction and writes an `audit_log` create row for every record, with `actor_subject` `system:seed`.
  - Refuses to run unless every table is empty.
- **`db:seed`, `db:reset` and the integration tests only run against local databases.** They refuse:
  - `NODE_ENV=production`
  - any host other than `localhost`, `127.0.0.1`, `[::1]` or `db`
  - a `DATABASE_URL` with a `host` or `hostaddr` query parameter, because node-postgres lets those override the host in the URL
- **`db:reset` also checks what's in the database before dropping anything,** so a tunnel to a real database on `localhost` is still refused (`dropAppObjects` in `src/db/reset.ts`).
  - **Allowed:** an empty database, a migrated database with no data, or a seeded development database (including edits made in it), as long as every row has a `create` entry in `audit_log`.
  - **Refused:** tables or views this app doesn't create (in `public` or `drizzle`), any imported data (`system:` audit entries other than the seed's), data in a database that was never seeded, rows with no audit record of being created, or anything else that depends on the app's tables, views or enums.
  - **The check and the drop run in one transaction.** The app's tables are locked before their contents are checked, so an import can't commit in between.
  - **Only the app's own objects are dropped,** by name and without `CASCADE`. Anything else in the database is left alone.
  - To start again with a local database that holds imported data, run `docker compose down -v`.
- **The integration tests run in `npm test`.** Each run creates `gdshub_test_<random>` on the `DATABASE_URL` server and drops it afterwards. Vitest reads `DATABASE_URL` from `.env` (an environment variable wins, as in CI), and the tests fail with a clear message if it isn't set. The database user needs `CREATEDB`. The compose and CI users are superusers.
- **The database scripts load `.env` with Node's `--env-file-if-exists` and run TypeScript through `--import tsx`.** In CI they use the environment instead.
- **CI checks that the migrations match the schema.** The lint job runs `npm run db:generate` and fails if `drizzle/` changes.

## Steps to run on the host

The packages (`drizzle-orm`, `pg`, `drizzle-kit`, `@types/pg`) were installed by the developer during the session. Then:

```sh
docker compose up -d db

# 1. Generate the table migration from the schema
npm run db:generate -- --name=init

# 2. Register the hand-written search migration (once only: each run adds
#    another journal entry). drizzle-kit overwrites the file with a stub, so
#    keep a copy and put it back.
cp drizzle/0001_search.sql /tmp/0001_search.sql
npx drizzle-kit generate --custom --name=search
cp /tmp/0001_search.sql drizzle/0001_search.sql

# 3. Register the hand-written audit_log migration the same way (once only)
cp drizzle/0002_audit_log_append_only.sql /tmp/0002_audit_log_append_only.sql
npx drizzle-kit generate --custom --name=audit_log_append_only
cp /tmp/0002_audit_log_append_only.sql drizzle/0002_audit_log_append_only.sql

# 4. Check
npm run db:reset
npm run format     # Prettier couldn't run in the sandbox
npm run lint && npm run typecheck && npm test && npm run test:e2e
```

Check that `drizzle/meta/_journal.json` lists `0000_init`, `0001_search` and `0002_audit_log_append_only`, in that order. Commit `drizzle/` including `meta/`.
